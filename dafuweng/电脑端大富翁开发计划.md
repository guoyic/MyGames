# 电脑端大富翁类游戏开发计划

## 0. 项目概述

### 0.1 项目目标

开发一个电脑端 2D 大富翁类游戏，支持本地多人游玩，并逐步扩展 AI、存档、事件卡、交易、地图编辑器等功能。

项目优先目标不是一开始做出完整商业级游戏，而是先完成一个可玩的最小版本，然后持续迭代。

### 0.2 游戏类型

- 类型：回合制棋盘策略游戏
- 平台：Windows / macOS / Linux 桌面端
- 视角：2D 俯视棋盘
- 玩家人数：2—4 人
- 操作方式：鼠标点击为主，键盘辅助
- 游戏模式：
  - 本地多人轮流操作
  - 后续可加入 AI 玩家
  - 后续可加入局域网或在线联机

### 0.3 推荐技术栈

优先推荐：

- 引擎：Godot 4
- 语言：GDScript
- 资源格式：PNG / SVG / OGG / JSON
- 版本管理：Git
- 项目管理：GitHub Projects / Notion / 飞书文档均可

如果你更熟悉 Unity，也可以使用 Unity + C#。但对于 2D 回合制桌游，Godot 会更轻量，开发效率更高。

## 1. 开发原则

### 1.1 先做最小可玩版本

第一阶段只追求“能完整玩一局”，不要一开始做复杂系统。

第一版必须能完成：

1. 创建游戏
2. 玩家轮流行动
3. 掷骰子
4. 棋子移动
5. 到达地块后触发事件
6. 买地
7. 收租
8. 玩家破产
9. 判定胜利

### 1.2 数据和逻辑分离

棋盘、地产、卡牌、角色初始属性等都应该用数据文件配置，不要全部写死在代码里。

建议使用：

```text
data/
  board_tiles.json
  property_rules.json
  chance_cards.json
  player_config.json
```

这样后续可以方便扩展地图和规则。

### 1.3 先保证逻辑正确，再做表现

开发顺序应该是：

1. 核心规则
2. 状态管理
3. UI 显示
4. 动画表现
5. 音效和美术
6. 扩展玩法

不要在规则还没跑通之前投入太多美术和动画。

## 3. 核心玩法设计

### 3.1 玩家属性

每个玩家至少需要以下字段：

```text
Player
  id
  name
  color
  money
  position
  properties
  status
  is_ai
  jail_turns
```

说明：

- `id`：玩家编号
- `name`：玩家名
- `color`：棋子颜色
- `money`：当前资金
- `position`：当前所在格子编号
- `properties`：拥有的地产列表
- `status`：正常、破产、暂停行动等
- `is_ai`：是否为 AI
- `jail_turns`：如果设计监狱机制，可用于记录剩余回合

### 3.2 棋盘格子类型

第一版建议设计 28—40 个格子。可以先做 28 格，降低工作量。

格子类型建议：

```text
START          起点
PROPERTY       普通地产
TAX            税收
CHANCE         机会卡
DESTINY        命运卡
JAIL           监狱 / 停留
GO_TO_JAIL     进入监狱
BONUS          奖励
PENALTY        惩罚
EMPTY          空地
```

MVP 阶段至少需要：

- 起点
- 普通地产
- 税收
- 机会卡
- 奖励格
- 惩罚格

### 3.3 地产属性

地产数据结构：

```text
Property
  tile_id
  name
  group
  price
  base_rent
  house_level
  max_house_level
  house_cost
  owner_id
  mortgage_status
```

MVP 可以暂时不做抵押，只保留字段，后续再启用。

### 3.4 回合流程

一个标准回合：

```text
当前玩家回合开始
  ↓
判断玩家状态
  ↓
玩家点击“掷骰子”
  ↓
生成骰子点数
  ↓
棋子移动
  ↓
判断是否经过起点
  ↓
触发落点事件
  ↓
玩家进行购买 / 支付 / 抽卡等操作
  ↓
判断是否破产
  ↓
判断是否胜利
  ↓
切换到下一位玩家
```

### 3.5 胜利条件

MVP 建议使用两种胜利条件之一：

#### 方案 A：破产淘汰制

当只剩一名玩家没有破产时，该玩家获胜。

优点：

- 接近传统玩法
- 规则直观

缺点：

- 游戏时间可能较长
- 被淘汰玩家体验差

#### 方案 B：限时资产制

设定最大回合数，比如 30 回合。结束后统计总资产：

```text
总资产 = 现金 + 地产购买价 + 房屋价值
```

总资产最高者获胜。

优点：

- 更适合电脑端快节奏游戏
- 不容易拖太久
- 适合野餐、休闲、直播、联机

建议第一版同时支持：

- 破产模式
- 30 回合限时模式

## 6. 核心模块设计

### 6.1 GameManager

职责：

- 管理游戏全局状态
- 初始化游戏
- 判断胜负
- 控制场景切换

关键方法：

```text
start_game(config)
restart_game()
end_game()
check_victory()
save_game()
load_game()
```

### 6.2 TurnManager

职责：

- 控制当前玩家
- 管理回合阶段
- 切换玩家

关键方法：

```text
start_turn(player)
roll_dice()
finish_movement()
resolve_tile()
end_turn()
next_player()
```

回合阶段建议使用枚举：

```text
WAITING_ROLL
MOVING
RESOLVING_TILE
WAITING_DECISION
TURN_END
GAME_OVER
```

这样可以避免玩家在错误阶段点击按钮。

### 6.3 BoardManager

职责：

- 加载棋盘
- 提供格子查询
- 提供路径查询

关键方法：

```text
load_board_data()
get_tile(tile_id)
get_next_position(current_position, steps)
get_tile_world_position(tile_id)
```

### 6.4 PlayerManager

职责：

- 创建玩家
- 查询玩家状态
- 管理玩家列表

关键方法：

```text
create_players(config)
get_current_player()
get_active_players()
mark_bankrupt(player)
```

### 6.5 EconomyManager

职责：

- 管理资金变化
- 处理玩家之间的转账
- 计算资产

关键方法：

```text
add_money(player, amount)
remove_money(player, amount)
transfer_money(from_player, to_player, amount)
calculate_assets(player)
```

### 6.6 EventManager

职责：

- 处理地块效果
- 处理事件卡效果

关键方法：

```text
resolve_tile_event(player, tile)
draw_chance_card()
apply_card_effect(player, card)
```

### 6.7 UIManager

职责：

- 刷新玩家面板
- 弹出确认框
- 显示提示文本
- 显示结算界面

关键方法：

```text
update_player_panels()
show_message(text)
show_purchase_dialog(property)
show_card_dialog(card)
show_game_over_screen(ranking)
```

## 阶段 8：基础 AI

预计时间：5—8 天

目标：实现可以陪玩的简单 AI。

AI 决策先不用复杂，只做规则判断：

### 8.1 AI 买地规则

```text
如果现金 >= 地产价格 + 安全现金线，则购买
否则不购买
```

例如：

```text
安全现金线 = 300
```

### 8.2 AI 事件处理

AI 自动执行事件，无需玩家选择。

### 8.3 AI 后续扩展

可以加入更复杂决策：

- 根据地产颜色组判断是否购买
- 根据现金流判断是否建房
- 根据对手资产判断是否交易
- 根据收益率决定地产价值

## 12. 常见风险与解决方案

### 12.1 游戏时间太长

问题：

- 大富翁类游戏容易拖到 1 小时以上。

解决：

- 加入最大回合数
- 增加起始资金差异
- 提高租金
- 减少地图格子数量
- 增加事件卡影响

### 12.2 玩家破产后无事可做

问题：

- 淘汰制会让玩家提前退出体验。

解决：

- 支持限时资产模式
- 破产玩家可以转为“幽灵事件”玩家
- 破产后仍可投票触发公共事件
- 设计复活机制

MVP 阶段可先不解决，但最终版本建议加入限时资产模式。

### 12.3 规则越来越复杂

问题：

- 建房、交易、抵押、拍卖会让代码迅速复杂。

解决：

- 每个系统独立实现
- 不要在 TurnManager 中写全部逻辑
- 使用状态机管理回合阶段
- 所有规则先写到 `rules.md`

### 12.4 UI 逻辑混乱

问题：

- 回合制游戏经常出现按钮在错误阶段可点击。

解决：

- 使用回合阶段枚举
- 每个阶段只开放对应按钮
- UI 只调用管理器，不直接修改数据

### 12.5 存档恢复困难

问题：

- 如果数据结构混乱，后期很难做存档。

解决：

- 从一开始就把游戏状态集中到可序列化对象
- 不要把关键状态散落在 UI 节点里
- 所有状态都应能转成 JSON
